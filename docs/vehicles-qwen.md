# Консультация Qwen4-Max: машины в изометрии (18.11.2026)

# Диагноз подтверждён

Iso-спрайт — это уже спроецированный 3D-объект. `ctx.rotate` применяет 2D-поворот к результату проекции, а нужен поворот **до** проекции. Единственный корректный путь при фиксированной камере — **турнтейбл: набор предрендеров + снап курса**. Всё остальное (морф, warp, shear) — костыли поверх этого.

Ниже — числа, математика и план.

---

## 1. Сколько направлений, снап, переходы

### 1.1. Ключевая ловушка вашей проекции

В 2:1 iso экранный угол НЕ равен мировому. Проекция: `sx = 32(x−y)`, `sy = 16(x+y)`. Для курса θ:

```
u = θ + 45°
sx = 45.25·cos(u),  sy = 22.6·sin(u)   [px на метр]
φ_screen = atan( tan(u) / 2 )
```

Производная `dφ/dθ` гуляет от **0.5** (машина боком, едет влево/вправо) до **2.0** (машина едет «в камеру»/«от камеры», вдоль экранной вертикали).

**Это и есть ваш баг «встаёт на дыбы»**: около экранной вертикали ошибка курса удваивается. Равномерный снап в мировом угле даёт неравномерную ошибку на экране.

### 1.2. Таблица ошибок (седан ~4.2 м, полудлина 2.1 м, спрайт ~170 px)

| N | шаг | макс. ошибка мира | макс. ошибка **на экране** | снос носа, px | кадров с учётом флипа |
|---|---|---|---|---|---|
| 8 | 45° | 22.5° | **~40°** | 19–35 | 5 |
| **16** | 22.5° | 11.25° | **~22°** | 9–18 | 9 |
| 24 | 15° | 7.5° | ~15° | 6–12 | 13 |
| **32** | 11.25° | 5.6° | **~11°** | 5–9 | 17 |

Снос носа в px — это расстояние между «где должен быть капот» и «где он нарисован». Ширина машины на экране ~45–60 px. То есть:

- **8 направлений**: капот уезжает на ⅔ ширины кузова → машина явно «крабит» боком. Ломается.
- **16**: до половины ширины, в движении читается нормально, на стоянке с рулём — заметно.
- **32**: ошибка меньше толщины колеса → глаз не ловит.

### 1.3. Рекомендация

- **MVP: 16 направлений.** Это порог «едет и читается».
- **Машина игрока: 16 + гибридная доводка (п.3)** или 32, если атлас не жалко.
- **Остов/статичный декор: 8够了** — он не едет, ошибку курса не с чем сравнить.
- **8 для ездящего трафика — не берите.** Экономия 4 кадра не стоит 40° ошибки.

**8 vs 16 на 170 px — разница восприятия:** на 8 при повороте руля машина «прыгает» между позами, глаз читает это как телепорт, а не как поворот. На 16 при скорости >3 м/с переходы почти не читаются (маскируются_own_ движением), проблема остаётся только на месте/парковке. На 32 проблема исчезает полностью.

### 1.4. Снап с гистерезисом (обязательно, иначе дребезг на границе)

```js
const N = 16, STEP = Math.PI * 2 / N;
const HYST = 0.13;            // ±2.9° мирового курса
const OFFSET = 0;             // курс, при котором рисуется кадр 0

function pickDir(heading, prev) {
  const f = (heading - OFFSET) / STEP;
  const nearest = Math.round(f);
  // не переключаемся, пока не вышли за границу + гистерезис
  const delta = Math.abs(f - prev);
  const wrapped = Math.min(delta, N - delta);
  const idx = (wrapped < 0.5 + HYST) ? prev : nearest;
  return ((idx % N) + N) % N;
}
```

Плюс сглаживание курса **только для выбора кадра** (физика остаётся сырой):
`visualHeading += angDiff(heading, visualHeading) * (1 - exp(-dt/0.07))` — τ ≈ 70 мс.

### 1.5. Переход между кадрами

- **Морф/варп — нет.** Резиновая машина, дорого, выглядит хуже попа.
- **Мгновенно — ок при 32 направлениях и на скорости.**
- **Кроссфейд — ваш вариант при 16.** Два `drawImage` с альфой, 60–100 мс.

Длительность адаптивная, чтобы не «двоился» капот на медленном манёвре:

```js
const omegaScreen = /* рад/с экранного угла φ */;
const T = clamp(0.5 * STEP / max(omegaScreen, 0.01), 0.04, 0.11);
```

Призрак двух носов на 18 px в течение 4 кадров при 60 fps — приемлемо в движении, заметно на стоянке. Поэтому: **на скорости <1 м/с кроссфейд укорачиваем до 40 мс и включаем микроповорот (п.3), на скорости >4 м/с — можно вообще без фейда.**

## 2. Производство ассетов: честно про Gemini

### 2.1. Реалистичная оценка

**Консистентную серию из 8–16 поворотов одной машины текстом через Gemini вы не получите.** Причины:

- Диффузионка не имеет 3D-представления объекта. Запрос «тот же седан, повёрнутый на 22.5°» меняет колеёю, форму фар, радиус арок, положение стоек.
- Image-to-image с референсом держит объект примерно до ±30° поворота, дальше — переизобретает.
- Ортoграфическая камера с точным elevation 30° не выдерживается: разброс ±10–15°, а вам нужен ровно один угол для всей серии.
- Тень «запекается» в кадр под разным углом → машина «плавает» над землёй.

Ожидаемый выход (оценка по опыту, не гарантия): **1 пригодный кадр из 8–15 генераций**, и даже пригодные кадры между собой не совпадут по пропорциям. На 9 уникальных кадров × 3 типа кузова это 1–3 дня черри-пикинга и ручной нормализации, с результатом «терпимо, но видно».

### 2.2. Если всё же Gemini — единственный работающий рецепт

1. **Один лист-турнтейбл, а не 8 отдельных промптов.** «Sprite sheet, 8 views of the SAME car, orthographic isometric, 30° elevation, arranged in 2×4 grid, flat neutral grey background, uniform top lighting, no cast shadow, no text». Модель внутри одного изображения attends к одному объекту — консистентность заметно выше, чем между генерациями. Генерируйте 4–6 листов, берите лучший.
2. **Свет строго сверху-сзади** (азимут = экранная вертикаль, elevation 55–65°). Тогда горизонтальный флип почти не меняет шейдинг — это критично для п.4.
3. **Никаких надписей, номеров, логотипов** — при зеркалировании читаются задом наперёд.
4. **Нормализация батчем (это и склеивает серию в «одну машину»):**
   - вырезание, удаление запечённой тени полностью;
   - выравнивание по **центру колёсной базы**, спроецированному на землю (не по центру bbox! свес капота ломает выравнивание);
   - масштаб по колёсной базе, а не по габариту;
   - downscale до целевых ~170 px → квантование в 16 цветов одной палитрой → 1 px тёмный контур через дилатацию альфы.
   
   **Единая палитра + единый контур + единый якорь дают ~80% ощущения «одна машина».** Фото-детали на 170 px всё равно превращаются в кашу.
5. Тень рисуем процедурно (п.3.3), всегда одинаковую.

### 2.3. Настоятельная рекомендация: Blender-турнтейбл

Это решает задачу полностью за **2–4 часа**, а не за 2 дня. Low-poly машина (Kenney Car Kit / Quaternius — CC0, или Sketchfab CC-BY), 3 материала на одном меше: седан / фургон / остов.

Точные параметры сцены под вашу проекцию:

```
Camera: ORTHOGRAPHIC
Rotation X = 60°   (=> elevation 30°, sin30 = 0.5 => ровно 2:1)
Rotation Z = 45° + k * (360/N),  k = 0..N-1
ortho_scale = renderWidth / (32 * sqrt(2))     # 512 px -> 11.314 м
Light: SUN, elevation 60°, азимут сверху-сзади, energy ~3
Film: transparent, Color Management: Standard (не Filmic!)
Output: 512×512 PNG, даунскейл ×0.5 -> 256×256, 32 px/м по осям
```

**Проверочный тест:** отрендерьте куб 1×1 м на земле — он обязан дать ровно **64×32 px** ромб. Если да — проекция совпала с вашей игрой попиксельно.

> Нюанс: при физически честной камере 30° вертикаль масштабируется как `32·√2·cos30 ≈ 39.2 px/м`, а не 32. Если ваш движок рисует высоту как `z*32`, для машины разница ≤6 px — забейте. Для зданий потом решите отдельно.

Пайтон-скрипт на 25 строк крутит камеру и рендерит цикл. Что вы получаете бесплатно:

- **идеальная консистентность** всех N кадров и всех 3 кузовов;
- **32 направления вместо 16 — та же цена** (просто `N=32`);
- отдельные пассы: **маска колёс**, **AO/тень**, **эмиссия фар** — как отдельные слои;
- смена состояния (битая, горит, остов) = смена материала на том же меше;
- перекраска трафика = Hue-сдвиг одного атласа, 20 вариантов цвета бесплатно.

**Атлас:** 16 кадров × 256 px = сетка 4×4, 1024×1024 RGBA ≈ 4 МБ в памяти. 32 кадра = 2048×1024 ≈ 8 МБ. 3 типа × 32 кадра = 24 МБ — нормально для браузера. Храните JSON с якорем `(ax, ay)` для каждого кадра.

**Гибрид, если хочется «AI-стиля»:** сгенерируйте Gemini текстуры/детали и наложите на low-poly меш, либо используйте AI-рендер как референс для тональной коррекции Blender-кадров. 3D даёт геометрию и консистентность, AI — фактуру.

## 3. Гибрид «снап + микроповорот» — да, практикуется, но не так, как вы описали

### 3.1. Почему ±22.5° — слишком много

Вы предложили доворачивать на полный полушаг. При 16 направлениях полушаг 11.25° мирового = **до 22° экранного** около вертикали. Это ровно тот режим, где `ctx.rotate` ломает картинку. Порог, где 2D-поворот ещё читается как 3D-поворот: **≤6–8° экранного угла**.

### 3.2. Правильная математика: поворот в плоскости земли

Поворот объекта **на земле** на Δθ в экранном пространстве — это не `rotate`, а линейное отображение `T = A·R(Δθ)·A⁻¹`, где `A = [[32,−32],[16,16]]`. Разворачивается в красивое:

```
T = | cos Δ    −2·sin Δ |
    | 0.5·sinΔ    cos Δ |
```

`det T = 1` — площадь сохраняется. Это точный поворот для всего, что лежит на земле (тень, пятна колёс, следы). Для кузова он даёт лёгкий сдвиг-скос, который **выглядит как поворот, а не как «вставание на дыбы»** — потому что не поднимает крышу.

### 3.3. Рецепт послойно (это и есть правильный гибрид)

```js
// 1. ТЕНЬ — всегда точная, процедурная, под любым курсом
ctx.save();
ctx.translate(sx, sy);
ctx.transform(c, 0.5*s, -2*s, c, 0, 0);   // T для ПОЛНОГО курса, не остатка
ctx.globalAlpha = 0.35;
ctx.drawImage(shadowSprite, -w/2, -h/2);  // эллипс/скруглённый прямоугольник 4.2×1.8 м
ctx.restore();

// 2. КУЗОВ — снапнутый кадр + демпфированный остаток
const dPhi = screenAngle(heading) - screenAngle(dirHeading);  // остаток
const k = 0.5;                                                 // демпфер
const rot = clamp(k * dPhi, -8*DEG, +8*DEG);
ctx.save();
ctx.translate(sx, sy);          // якорь = центр колёсной базы на ЗЕМЛЕ
ctx.rotate(rot);
ctx.translate(-ax, -ay);        // якорь кадра из JSON, НЕ центр спрайта
ctx.drawImage(atlas, ...);
ctx.restore();
```

Три правила, без которых гибрид не работает:
1. **Пивот — точка контакта с землёй** (центр колёсной базы), не центр bbox. Иначе машина «orbit»-ит вокруг себя.
2. **Демпфер k ≈ 0.5** и **клэмп ±8° экранного**. Остаток гасится наполовину — глаз не считает половину, но ломаться перестаёт.
3. **Тень не снапится никогда.** Точная тень под полным курсом «якорит» восприятие сильнее, чем сам спрайт. Это самый дешёвый и самый эффективный трюк во всём ответе.

Практикуется ли: да, снап + мелкая доводка — стандартная схема 2D-гонок с предрендером (GTA 1/2, Micro Machines и потомки). Там предрендеров было десятки, а доводка — единицы градусов.

### 3.4. Бонус: 3D-якоря для эффектов

Храните в конфиге машины 3D-точки: фары `(±0.7, 2.0, 0.6)`, стопы `(±0.7, −2.0, 0.6)`, выхлоп. Проецируйте их **точно** через поворот курса + iso-матрицу, независимо от кадра спрайта. Тогда стоп-сигналы, блики, дым и искры всегда на месте, даже когда кузов снапнут. Стоит 20 строк, даёт непропорционально много «сочности».

## 4. Зеркалирование: вам нужно меньше кадров, чем вы думаете

### 4.1. Математика

Горизонтальный флип экрана в вашей проекции = отражение мира относительно плоскости `x = y`. Это отображает курс **θ → 90° − θ**.

Проверка: множество из 16 курсов замкнуто относительно этого (`k → (4−k) mod 16`). Неподвижные точки — k=2 и k=10 (курсы 45° и 225°, «прямо в камеру» и «прямо от камеры»), они обязаны быть симметричными.

**Итого: 9 уникальных рендеров + 7 флипов = 16 направлений.** Для 8 — 5+3. Для 32 — 17+15.

### 4.2. Ответ на ваш вопрос

**Отдельные кадры «едет вниз-влево» vs «вверх-вправо» не нужны** — это не зеркальная пара. Зеркальная пара — это «едет вниз-влево» ↔ «едет вниз-вправо» (относительно экранной вертикали). Пара «вниз-влево / вверх-вправо» — это разворот на 180°, отдельный честный кадр (капот и багажник разные).

### 4.3. Условия, при которых флип не палится

- **Якорь флипа — вертикаль через центр колёсной базы**, не через центр bbox. Свес капота несимметричен → машина прыгнет на 3–8 px при переключении.
- **Свет сверху-сзади** (азимут вдоль экранной вертикали). Тогда флип меняет только мелкий блик.
- **Водитель за рулём**: на 170 px через лобовое видно руль слева. Флип переносит его направо. В 95% игр это никого не волнует; если волнует — рендерите все 16.
- **Никакого текста на кузове.**

### 4.4. Но

**Если идёте через Blender — зеркальте только если лень.** Рендер всех 16 стоит те же 30 секунд, а асимметрия и свет остаются честными. Флип — это экономия ручного/AI труда, не машинного.

## 5. Порядок работ

### Итерация 1 — MVP «едет и читается» (1–2 дня)

| # | Задача | Время |

**Критерии приёмки (сделайте буквально):**
- Машина на круге R=8 м, v=4 м/с → на записи 60 fps не видно «ступенек», капот не отрывается от траектории больше чем на 15 px.

- Тень непрерывно вращается, ни разу не снапнулась.

Это уже играбельно и не стыдно показать.

### Итерация 2 — «выглядит дорого» (2–3 дня)

1. **32 направления для машины игрока** (`N=32` в скрипте, атлас 2048×1024). Трафик оставляем на 16.
2. **Гибрид-доводка**: демпфер 0.5, клэмп ±8°, пивот на земле — только при скорости <2 м/с.
3. **Слой колёс отдельным пассом** из Blender → передние колёса рисуем с реальным углом руля. Мгновенно даёт «живую» машину.
4. **3D-якоря**: стоп-сигналы (эмиссивный пасс), фары, дым из выхлопа, искры при контакте.
5. **Фургон + остов** тем же мешем/материалом — 30 минут рендера, идеальная консистентность.
6. **Перекраска трафика**: hue-shift атласа в offscreen-canvas на старте, 8–12 вариантов.

### Что НЕ делать

- ❌ Морфинг между кадрами.
- ❌ Поворот всего спрайта на полный остаток (>8° экранного).
- ❌ 8 направлений для ездящих машин.
- ❌ Запечённая в спрайт тень.
- ❌ attempting 16 консистентных кадров через Gemini текстом — это ловушка на 2 дня с плохим результатом.

## Короткий ответ на пять вопросов

1. **16** (не 8), **32** для машины игрока. Снап `round(θ/STEP)` + гистерезис ±3° + сглаживание 70 мс. Переход — кроссфейд 40–110 мс, не морф. Разница 8↔16 на 170 px: снос капота 35 px → 18 px, т.е. «сломано» → «нормально в движении».
2. **Gemini — нет** для консистентной серии; максимум лист-турнтейбл одним изображением + жёсткая нормализация (палитра 16 цветов, контур 1 px, якорь по колёсной базе, тень удалить). **Blender low-poly турнтейбл — 2–4 часа и идеальная консистентность**, это основной путь. Процедурная коробка — только как временный фолбэк.
3. **Да, но**: клэмп **±8° экранного** (не ±22.5° мирового), демпфер 0.5, пивот на земле, тень отдельно под полным курсом через `T = [[c,−2s],[0.5s,c]]`.
4. **Флип = θ→90−θ**, 9 кадров + 7 флипов = 16. Пара «вниз-влево / вверх-вправо» — это 180°, не флип. Свет сверху-сзади, якорь по колёсной базе, без надписей. Через Blender — просто рендерите все 16.
5. **Сначала**: Blender-турнтейбл 16 + снап с гистерезисом + процедурная тень + кроссфейд. **Потом**: 32 для игрока, микроповорот, отдельные колёса, 3D-якоря эффектов, варианты кузовов.
